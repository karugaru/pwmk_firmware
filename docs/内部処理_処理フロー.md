# 内部処理ドキュメント

## 処理フロー

### 前提

- デバイス入力、ペリフェラル、USB、BLE は 1ms 周期のメイン処理で順番に処理されます。
- BLE 有効時は CYW43 の async context ワーカーから 1ms 周期処理を呼び出し、BLE 無効時はメインループから直接呼び出します。
- USB タスクは、送信トランスポートとして USB と BLE のどちらを選択しているかにかかわらず、USB が有効なら毎周期呼び出します。これはUSBがマウント済みで送信可能かを確認するためです。
- キーマトリクスのスキャン結果はイベント処理へ渡され、レポートは接続状態と設定された優先順位に応じて USB または BLE へ送信されます。

### データレベル

- キーマトリクスのスキャン結果は、GPIOの状態を表す配列として保存されます。
- スキャン結果から、キーコードとその状態（押下/解放）を抽出し、内部HID状態として保存・管理します。
- 内部HID状態は、現在のキー状態やマウスの移動量、ホイールの移動量などを含むデータ構造です。
- HIDレポートは、内部HID状態に基づいて生成されるバイト列です。

### ユーザ側処理

- ユーザーコードで独自のイベント処理を行う場合、内部HID状態を更新し、イベント発生フラグを立てる必要があります。
- 直接内部HID状態を変更することも可能ですが、ユーティリティ関数を使用して変更することが推奨されます。(TODO:未実装)
- ユーザーコードのイベント処理は、対応するイベント処理経路から実行されます。メインループ用ユーザーフックは未実装です。
- 非標準のペリフェラル処理を行う場合などに、メインループでの処理を要求する必要があります。(TODO:未実装)

### 処理フロー概略

1. 1ms 周期処理：キーマトリクススキャン → 周期イベント処理 → USB/BLE タスク → ペリフェラル処理
2. HID イベント処理：内部HID状態の更新 → 選択中のトランスポートへ送信要求
3. HID レポート送信：USB は TinyUSB、BLE は btstack の送信可能イベントからレポートを送信

## 処理フロー詳細

1. 1ms 周期処理
   - 一定周期で呼び出され、以下の処理を行います。
   - キーマトリクスのスキャンを行い、キー入力検出を行います。
     - キー状態に変更があった場合、ユーザ定義イベント処理と標準イベント処理を実行します。
     - これは内部HID状態を更新します。
   - USB が有効なら `usb_hid_task()` を呼び出し、Vial Raw HID の受信要求もメイン処理で実行します。
   - BLE が有効なら `ble_poll()` を呼び出します。
   - ペリフェラル処理が必要な場合は I2C を含む処理を実行します。
   - イベントがある場合、BLE 接続中は BLE、そうでなければ USB を送信先として選択します。接続優先設定により選択順を変更します。
2. USB HID レポート送信処理
   - USB がマウント済みで送信可能な場合に、イベントキューのレポートを TinyUSB へ渡します。
3. BLE HID レポート送信処理
   - btstack の送信可能イベントで、イベントキューのレポートを送信します。
4. 低電力遷移
   - 無操作時間が設定値を超えると、RP2040 はマトリクス列または Pinnacle の DR ピンで DORMANT から復帰し、復帰後に watchdog reboot します。
   - RP2350 は現状 Pinnacle の DR ピンだけを PSTATE 復帰に使用し、復帰後は電源再起動と同じ状態になります。マトリクス復帰は未実装です。
5. BLE スロット管理
   - 選択中の BLE スロットは、`ble_persist_selected_slot` が有効なら再起動後も復元されます。
   - スロットごとのボンド情報と Advertising アドレスの世代番号を TLV へ保存します。
   - 選択スロットのボンドを解除すると世代番号を進め、次回 Advertising のアドレスを変更して旧ホストとの自動再接続を避けます。
