# Vial 互換外部仕様書

## 1. 目的

この文書は、Vial GUI / Configurator が期待する外部インターフェースを説明するものです。

- 受信した 32 バイトパケットに対し、どのコマンドを解釈し、どのバイトを返すべきかが明確である
- キーマップ、マクロ、動的エントリなどのデータが、どのバイト配列として扱われるかが明確である
- ロック状態、アンロック状態、書き込み拒否の挙動が明確である
- 互換実装者が、実装言語・OS・ハードウェアに依存しない形で実装できる

---

## 2. 基本前提

### 2.1 伝送方式

- 伝送路は USB HID の Raw Report として扱う。
- リポートIDは 0x00 とするので、HIDディスクリプタにはレポートIDなしで 32 バイトの Raw Report を定義する。
- 1 パケットの長さは固定で 32 バイトとする。
- ホストから送られたバッファを、そのまま応答用バッファとして再利用する。
- 受信時にパケット長が 32 バイトでない場合は、無視してよい。

### 2.2 パケットの基本形式

- Vial 固有コマンドは、先頭 1 バイト目に 0xFE を置く。
- その次のバイトにサブコマンド ID を置く。
- VIA 互換コマンドは、先頭 1 バイト目にコマンド ID を置く。
- すべての 2 バイト値は、必要に応じてビッグエンディアンまたはリトルエンディアンで記述する。
- そのどちらかが明示されていない場合は、以下のルールを採用する。
  - Vial 固有のサイズ・プロトコルバージョン・UID などはリトルエンディアン
  - キーマップやキーコードなどのバッファ転送は、16 ビットキーコードをビッグエンディアンで送る
- 文字列やバイナリデータは、NUL 終端文字列または固定長バイト列として扱う。

### 2.3 バッファ初期化のルール

- 応答を返す前に、未使用のバイトは 0x00 で埋めることが望ましい。
- ただし、特定のコマンドでは「未対応」を表すために 0xFF で埋めることがある。
- 受信した入力バッファの内容は変更してよく、応答時にはその内容を返す。

---

## 3. パケットの意味とオフセット

### 3.1 共通のバイト位置

- byte 0: コマンド ID または Vial プレフィックス
- byte 1: サブコマンド ID（Vial コマンド時）
- byte 2..31: コマンド固有の引数・応答データ

### 3.2 端数・不足データの扱い

- コマンドに必要な引数が不足している場合、応答は 0 で埋めるか、何も返さない。
- 受け付けるべき最大のデータ長は 32 バイトである。
- 1 パケットで渡せるデータ量を超える場合は、複数パケットに分割して取得・設定する。

### 3.3 ホスト実装が前提とする応答オフセット

- ホスト実装は、USB HID Raw Report のペイロードとして 32 バイト固定長を前提にする。実際の HID 転送では report ID として 0x00 を付けることがあるが、Vial/VIA プロトコル本体はその後ろの 32 バイトに収める。
- GET 系コマンドでは、応答の先頭にコマンド ID をエコーし、その後に実データを置くことを前提にする。例えば `0x01` / `0x02` / `0x0C` / `0x0D` は、byte 0 にコマンド、byte 1 以降に応答データが置かれる。
- `0x0E` (Macro Buffer Get) と `0x12` (Dynamic Keymap Buffer Get) では、ホストは応答の先頭 4 バイトを元のリクエストのエコーとして扱い、実データは byte 4 から始まると見なす。つまり `data[4:4+size]` を実際のバッファとして扱う。
- いずれの応答でも、未使用のバイトは 0x00 で埋めることが望ましく、ホストは不足分を 0x00 として扱ってもよい。

## 4. Vial 固有コマンド仕様

以下の各コマンドは、byte 0 = 0xFE で始まる。byte 1 にサブコマンド ID を置く。

### 4.1 0x00: Keyboard ID / Protocol Query

- 役割: キーボード固有 ID と Vial プロトコルのバージョンを返す
- リクエスト: 32 バイトバッファで、byte 0 = 0xFE, byte 1 = 0x00
- レスポンス:
  - byte 0..3: Vial プロトコルバージョン（リトルエンディアン）
  - byte 4..11: 8 バイトのキーボード UID
  - byte 12: サポートフラグ（VialRGB などがある場合は 1、それ以外は 0）
  - byte 13..31: 0x00 または未使用領域
- 実装上の要件:
  - UID は機器ごとに一意であること
  - プロトコルバージョンは、互換性を示す整数として返す

### 4.2 0x01: Keyboard Definition Size Query

- 役割: キーボード定義データの総サイズを返す
- リクエスト: byte 0 = 0xFE, byte 1 = 0x01
- レスポンス:
  - byte 0..3: 定義サイズ（リトルエンディアン）
  - byte 4..31: 0x00
- 実装上の要件:
  - 定義データのバイト数を返す
  - 0 を返してはいけない

### 4.3 0x02: Keyboard Definition Data Query

- 役割: キーボード定義データを 32 バイトごとのページとして返す
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x02
  - byte 2..3: page index（リトルエンディアン、0-origin）
- レスポンス:
  - 32 バイト分の定義データを返す
  - 先頭から page × 32 バイト目を開始し、必要な分だけを詰める
  - 範囲外なら 0x00 で埋める
- 実装上の要件:
  - 定義データは固定長ページ単位で返すこと
  - 1 ページあたりの長さは 32 バイトであること
  - ホストは、返されたページを連結した後に LZMA 圧縮を解凍し、その結果を JSON として解釈する前提である

#### 4.3.1 Keyboard Definition Data の実体

- 定義データの実体は、単なる「文字列」ではなく、LZMA 圧縮済みの JSON バイト列である。
- 期待される JSON の主要構造は以下の通りである。
  - `matrix.rows`: 物理的なキーの行数
  - `matrix.cols`: 物理的なキーの列数
  - `layouts.keymap`: KLE 互換の 2 次元レイアウト配列。各要素は文字列または辞書であり、ホスト側でキーレイアウトの物理配置を生成するために使用される
  - `layouts.labels`: 任意のレイアウトラベル配列
  - `lighting`: 任意の照明種別（例: `none`, `qmk_rgblight`, `vialrgb`）
  - `customKeycodes`: 任意のカスタムキーコード定義
  - `vial`: 任意の Vial 互換設定（例: `vibl`, `midi`）
- `layouts.keymap` の各セルが文字列の場合、ホストは KLE 形式のラベルとして解釈する。特に `labels[4] == "e"` をエンコーダとみなし、`labels[0]` の `row,col` 形式や `idx,direction` 形式を位置情報として解釈する。
- さらに、ホストは `labels[8]` の `idx,opt` 形式をレイアウト選択情報として解釈し、各キーに対して `layout_index` / `layout_option` を割り当てる。`idx,opt` は `index,option` の 2 要素として解釈される。
- `layouts.keymap` の各セルが辞書の場合、ホストは KLE のメタデータ（回転・サイズ・色など）として扱う。
- 未知のフィールドは無視してよいが、少なくとも `matrix` と `layouts.keymap` が解釈可能であることが重要である。

#### 4.3.2 KLE 形式のデータ構造

- `layouts.keymap` は KLE 互換の「行ベース配列」であり、トップレベルは行の配列、各行は 1 つ以上のキー要素を持つ配列である。
- 各要素は、文字列または辞書のいずれかである。文字列は 1 つのキーを表し、改行区切りで 12 個のラベルスロットに分解される。
- 文字列のラベルは、`align` などの設定に応じて並び替えられ、ホストはその結果を 12 要素のラベル配列として扱う。
- 辞書要素は、その後ろに続くキーに適用するメタデータとして扱う。代表的なキーは以下のとおりである。
  - `r`, `rx`, `ry`: 回転角・回転基準点
  - `a`: ラベルの整列モード
  - `f`, `f2`, `fa`: フォントサイズ
  - `p`, `c`, `t`: プロファイル、色、文字色
  - `x`, `y`, `w`, `h`: 位置・サイズ
  - `x2`, `y2`, `w2`, `h2`: 2 次元サイズ/位置
  - `n`, `l`, `d`, `g`: 追加のキー属性（nub / stepped / decal / ghost）
  - `sm`, `sb`, `st`: スイッチ情報のメタデータ
- ホスト実装では、特に以下のラベル位置に意味を持たせることが多い。
  - `labels[0]`: `row,col` 形式または `idx,direction` 形式
  - `labels[4]`: `"e"` の場合はエンコーダとして扱う
  - `labels[8]`: `idx,opt` 形式としてレイアウト選択情報を解釈する
- 実装上は、未対応または未知のメタデータを単に無視してもよい。ただし、少なくとも基本的な文字列ラベルと、位置・サイズを表す基本メタデータは解釈できることが望ましい。
- 互換性を保つため、`layouts.keymap` は「文字列だけでなく、辞書によるメタデータを含む KLE 互換構造」として扱うことが重要である。

#### 4.3.3 Keyboard Definition Data の実装のヒント

Keyboard Definition Dataはファームウェアのコンパイル時に生成してバイナリとして埋め込むと実装しやすい。マイコン側で圧縮などを行うのは難しいため。

### 4.4 0x03: Encoder Get

- 役割: エンコーダの設定を取得する
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x03
  - byte 2: layer
  - byte 3: encoder index
- レスポンス:
  - byte 0..1: clockwise 方向のキーコード（ビッグエンディアン）
  - byte 2..3: counterclockwise 方向のキーコード（ビッグエンディアン）
  - byte 4..31: 0x00
- 実装上の要件:
  - 対応しない場合は 0 を返す
  - 2 バイトのキーコードを返す

### 4.5 0x04: Encoder Set

- 役割: エンコーダ設定を保存する
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x04
  - byte 2: layer
  - byte 3: encoder index
  - byte 4: direction selector
  - byte 5..6: keycode（ビッグエンディアン、low/high? 実装上は 2 バイトの値）
- レスポンス:
  - 受け付けた結果を返す。少なくとも 0x00 または 0x01 のいずれかを返す
  - 実装上は、成功時 0x00、失敗時 0x01 を返すのが妥当
- 実装上の要件:
  - ロック状態時は書き込みを拒否する

### 4.6 0x05: Unlock Status Query

- 役割: ロック状態・アンロック進行状態・アンロック用コンボの座標を返す
- リクエスト: byte 0 = 0xFE, byte 1 = 0x05
- レスポンス:
  - byte 0: unlocked フラグ（0: locked, 1: unlocked）
  - byte 1: unlock_in_progress フラグ
  - byte 2: remaining counter / progress value
  - byte 3..31: unlock combo の row/col ペア
- 実装上の要件:
  - ロックされていない場合、byte 0 = 1
  - アンロック中なら byte 1 = 1
  - 解除用キー座標は、2 バイトずつ row/col のペアとして格納する

### 4.7 0x06: Unlock Start

- 役割: アンロック手順を開始する
- リクエスト: byte 0 = 0xFE, byte 1 = 0x06
- レスポンス:
  - 受け付けたら、通常は 0x00 を返す
- 実装上の要件:
  - 解除進行フラグを有効化し、タイマー・カウンタを初期化する

### 4.8 0x07: Unlock Poll

- 役割: アンロックの進行状況を確認する
- リクエスト: byte 0 = 0xFE, byte 1 = 0x07
- レスポンス:
  - byte 0: unlocked status
  - byte 1: unlock in progress
  - byte 2: remaining counter
- 実装上の要件:
  - 必要なキーが押されている場合のみカウントを減らす
  - 一定時間経過後に成功条件を満たすと unlocked を 1 にする

### 4.9 0x08: Lock

- 役割: 変更可能状態をロックする
- リクエスト: byte 0 = 0xFE, byte 1 = 0x08
- レスポンス:
  - 受け付けたら 0x00 を返す
- 実装上の要件:
  - unlocked を 0 に戻す

### 4.10 0x09: QMK Settings Query

- 役割: 対応可能な QMK 設定 ID を問い合わせる
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x09
  - byte 2..3: query threshold or minimum qsid（リトルエンディアン）
- レスポンス:
  - 32 バイトの応答バッファに、対応する設定の情報を埋める
  - 未対応なら 0xFF で埋める
- 実装上の要件:
  - QMK SETTINGS 機能が無い場合は、「対応なし」を表す 0xFF を返す

### 4.11 0x0A: QMK Settings Get

- 役割: 指定した設定 ID の内容を取得する
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x0A
  - byte 2..3: qsid（リトルエンディアン）
- レスポンス:
  - byte 0: 値の長さまたはステータス
  - byte 1..31: 値データ
- 実装上の要件:
  - 取得できない場合は 0x00 または 0xFF を返す

### 4.12 0x0B: QMK Settings Set

- 役割: 指定した設定 ID に値を書き込む
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x0B
  - byte 2..3: qsid（リトルエンディアン）
  - byte 4..31: 設定データ
- レスポンス:
  - 成功/失敗を表す 1 バイトを返す
- 実装上の要件:
  - ロック状態では書き込みを拒否する

### 4.13 0x0C: QMK Settings Reset

- 役割: 設定値を初期化する
- リクエスト: byte 0 = 0xFE, byte 1 = 0x0C
- レスポンス:
  - 成功なら 0x00、失敗なら 0x01

### 4.14 0x0D: Dynamic Entry Operation

- 役割: タップダンス・コンボ・キーオーバーライドなどの動的エントリを取得/設定する
- リクエスト:
  - byte 0 = 0xFE
  - byte 1 = 0x0D
  - byte 2: subcommand
  - byte 3: index
  - byte 4..31: 追加データ
- レスポンス:
  - 取得時: byte 0..N へ構造体データを詰める
  - 設定時: 1 バイトのステータスを返す
- 実装上の要件:
  - 取得/設定ともに固定長の構造体サイズに合わせてデータを埋める
  - 取得時は `byte 0` をステータス、`byte 1..` を構造体データとして扱う。ホストは `byte 0 = 0` を成功、非 0 を失敗として扱う
  - 設定時は、送信データの本体が構造体のバイナリ列であることを前提にし、`byte 0` 以降にそのまま詰める
  - 未対応のサブコマンドは 0x00 を返す
  - `GET_NUMBER_OF_ENTRIES` では、応答の先頭 4 バイトに tap dance / combo / key override / alt repeat key の個数を返し、byte 4 のビットマスクに機能フラグを返す。ホストはこの順序を前提に解釈する

### 4.15 ホスト実装から見た追加要件

- ホストは、Vial プロトコルとして 0..6、VIA プロトコルとして 9 をサポート対象とし、それ以外の値は未対応として扱う。
- `CMD_VIAL_DYNAMIC_ENTRY_OP + DYNAMIC_VIAL_GET_NUMBER_OF_ENTRIES` に対する応答では、byte 0..3 にそれぞれ tap dance / combo / key override / alt repeat key の個数を返す。byte 4 の下位ビットは機能フラグとして扱い、bit 0 = caps_word、bit 1 = layer_lock、その他ビットは予約とする。Vial protocol >= 5 では `persistent_default_layer` を有効な機能として扱う。
- `CMD_VIAL_QMK_SETTINGS_QUERY` は、応答を 2 バイトの `qsid` 配列として解釈し、`0xFFFF` を終端として扱う。ホストは `0xFFFF` 以外の値を支持済み設定として収集する。
- `CMD_VIAL_QMK_SETTINGS_GET` / `SET` / `RESET` では、`byte 0 = 0` を成功、非 0 を失敗または未対応として扱う。`GET` では `byte 1..31` を値データとして解釈する。

## 5. VIA 互換コマンド仕様

以下は、Vial GUI の基礎機能としてよく利用される VIA 互換コマンドです。Vial はこれらをそのまま扱うことで、キーマップ・マクロ・レイヤー構造の編集を可能にします。

### 5.1 0x01: Get Protocol Version

- リクエスト: byte 0 = 0x01
- レスポンス:
  - byte 1..2: プロトコルバージョン（ビッグエンディアン）
- 実装上の要件:
  - 例: 0x0009

### 5.2 0x02: Get Keyboard Value

- リクエスト:
  - byte 0 = 0x02
  - byte 1: value_id
- レスポンス:
  - byte 1..N: 値データ
- 実装上の要件:
  - `uptime`, `layout_options`, `switch_matrix_state`, `firmware_version`, `device_indication` などを扱えるようにする

### 5.3 0x03: Set Keyboard Value

- リクエスト:
  - byte 0 = 0x03
  - byte 1: value_id
  - byte 2..31: 値データ
- レスポンス:
  - 変更結果を返す

### 5.4 0x04: Get Keycode

- リクエスト:
  - byte 0 = 0x04
  - byte 1: layer
  - byte 2: row
  - byte 3: column
- レスポンス:
  - byte 3..4: 2 バイトのキーコード（ビッグエンディアン）
- 実装上の要件:
  - 返すキーコードは 16 ビットであること

### 5.5 0x05: Set Keycode

- リクエスト:
  - byte 0 = 0x05
  - byte 1: layer
  - byte 2: row
  - byte 3: column
  - byte 4..5: keycode（ビッグエンディアン）
- レスポンス:
  - 変更成功時は 0x00 等のステータスを返す

### 5.6 0x06: Dynamic Keymap Reset

- リクエスト: byte 0 = 0x06
- レスポンス:
  - 受け付けたら 0x00 を返す
- 実装上の要件:
  - キーマップの全要素を初期値に戻す

### 5.7 0x0B: Bootloader Jump

- リクエスト: byte 0 = 0x0B
- レスポンス:
  - ブートローダーに遷移する前提なので期待しない。
- 実装上の要件:
  - ブートローダーモードに遷移する。

### 5.8 0x0C: Macro Count

- リクエスト: byte 0 = 0x0C
- レスポンス:
  - byte 1: マクロ数

### 5.9 0x0D: Macro Buffer Size

- リクエスト: byte 0 = 0x0D
- レスポンス:
  - byte 1..2: バッファサイズ（ビッグエンディアン）

### 5.10 0x0E: Macro Buffer Get

- リクエスト:
  - byte 0 = 0x0E
  - byte 1..2: offset（ビッグエンディアン）
  - byte 3: size（最大 28）
- レスポンス:
  - byte 3..N: 指定範囲のマクロバッファ

### 5.11 0x0F: Macro Buffer Set

- リクエスト:
  - byte 0 = 0x0F
  - byte 1..2: offset
  - byte 3: size
  - byte 4..31: データ
- レスポンス:
  - 成功なら 0x00
- 実装上の要件:
  - 書き込み中は、最後のバイトを non-zero として扱うことが望ましい
  - 書き込み完了後に 0x00 に戻す

### 5.12 0x11: Layer Count

- リクエスト: byte 0 = 0x11
- レスポンス:
  - byte 1: レイヤー数

### 5.13 0x12: Dynamic Keymap Buffer Get

- リクエスト:
  - byte 0 = 0x12
  - byte 1..2: offset
  - byte 3: size
- レスポンス:
  - byte 3..N: キーマップバッファ

### 5.14 Lighting / VialRGB 拡張 (ホスト実装依存)

- ホストは、VIA 互換の lighting 制御として `0x07` (Set Lighting Value), `0x08` (Get Lighting Value), `0x09` (Save Lighting State) を利用する。
- `0x07` / `0x08` の `value_id` には、QMK backlight / RGB の設定 ID と、VialRGB 用の `0x40` / `0x41` / `0x42` を使用する。`0x41` は mode の取得/設定に使われ、`0x42` は supported effects の問い合わせに使われる。
- `GET` 系では、応答の先頭にコマンド ID と `value_id` をエコーし、実データはその後ろに置かれる。ホストは `byte 2..N` を値として解釈する。
- `QMK RGBLIGHT` の各値は 1 バイトまたは 2 バイトのデータとして返される。VialRGB の `GET_INFO` は、プロトコルバージョン、最大輝度、サポート機能の一覧などを返す。

### 5.15 ホストが使用する Keyboard Value ID

- ホストは、キーマップ以外の状態を取得・設定するために `0x02` / `0x03` の keyboard value コマンドを利用する。
- `0x02` (`layout_options`) は 4 バイトの符号なし整数として扱う。`GET` では `byte 2..5` を 32 ビット整数として解釈し、`SET` では同じ 4 バイトを送る。
- `0x03` (`switch_matrix_state`) は、スイッチの押下状態をビットマップとして返す。ホストは、応答の先頭 2 バイトをスキップし、その後ろのバイト列を行ごとに解釈する。1 行あたりのバイト数は `ceil(cols / 8)` であり、各ビットは 1 キーに対応する。ホスト実装では、各行スライスの末尾から逆順にバイトを読むため、実装側もこの並びを尊重する必要がある。

### 5.16 Protocol Version による機能ゲート

- ホストは、機能ごとに別個の問い合わせを増やすのではなく、Vial のプロトコルバージョンを能力ゲートとして使う。
- 実装上の観測値として、以下のしきい値がホストで使われる。
  - `vial_protocol >= 2`: advanced macro サポート
  - `vial_protocol >= 3`: matrix tester / unlock-aware matrix polling サポート
  - `vial_protocol >= 4`: dynamic entry (tap dance / combo / alt repeat key) と QMK settings サポート
  - `vial_protocol >= 5`: extended macro と key override サポート
  - `vial_protocol >= 6`: 追加の dynamic entry 機能を扱う場合がある
- したがって、実装側は Vial protocol version を適切に返し、対応する機能が有効になる前にそのコマンド群を提供しないようにすることが望ましい。

## 6. データ構造の詳細

### 6.1 キーマップ

- 1 つのキーは 16 ビットのキーコードで表現する。
- キーマップの参照順は、レイヤー → 行 → 列である。
- 1 レイヤーのキー位置数は、物理レイアウトの行数 × 列数に対応する。
- 1 つのキーコードは、2 バイトの配列として扱う。
- ホスト実装では、キーマップバッファはビッグエンディアンの `>H` で読み書きされる。つまり 1 キーコードにつき 2 バイト、各レイヤーの行列を連続して並べる。
- `0x12` で取得するバッファは、レイヤー 0 から順に、各レイヤー内では row 0..rows-1、col 0..cols-1 の順で並ぶ。

### 6.2 マクロ

- 複数のマクロは、NUL 終端文字列の列として保持する。
- 1 つのマクロは、文字列として扱い、必要に応じて UTF-8 文字列として保存する。
- マクロバッファは、オフセットベースの連続データとして扱う。
- ホスト実装では、マクロは単純な文字列ではなく、QMK/ Vial 互換の命令列としてバイナリ化される。特に、protocol version 1 では 1 バイトコード + 1 バイト引数の形式、protocol version 2 では `0xFD` / `0xFE` 系の拡張命令を含める。ホストは、これを逐次的にデコードして UI 上のアクション列に復元する。
- `0x0E` / `0x0F` でやり取りされるバッファは、マクロの NUL で区切られた連続データとして扱い、`0x00` で終端する。ホストは、複数マクロの境界を把握するために、NUL 区切りで分解する。

### 6.3 レイヤー

- レイヤー数は、ホストが問い合わせ可能であること。
- 各レイヤーは同じ行列サイズを持つこと。
- レイヤー 0 を既定レイヤーとして扱う。

### 6.4 動的エントリ

#### 6.4.1 Tap Dance

- 10 バイト固定長
- フィールド:
  - 2 バイト: on_tap
  - 2 バイト: on_hold
  - 2 バイト: on_double_tap
  - 2 バイト: on_tap_hold
  - 2 バイト: custom_tapping_term
- 実装上の要件:
  - 16 ビット値なので、2 バイト単位のエンディアンを統一する

#### 6.4.2 Combo

- 10 バイト固定長
- フィールド:
  - 4 × 2 バイト: input[4]
  - 2 バイト: output
- 実装上の要件:
  - 入力キーの配列は 4 個まで

#### 6.4.3 Key Override

- 10 バイト固定長
- フィールド:
  - 2 バイト: trigger
  - 2 バイト: replacement
  - 2 バイト: layers
  - 1 バイト: trigger_mods
  - 1 バイト: negative_mod_mask
  - 1 バイト: suppressed_mods
  - 1 バイト: options
- 実装上の要件:
  - `options` の各ビットは、実装側の機能フラグとして扱う

#### 6.4.4 Alt Repeat Key

- 6 バイト固定長
- フィールド:
  - 2 バイト: keycode
  - 2 バイト: alt_keycode
  - 1 バイト: allowed_mods
  - 1 バイト: options

## 7. セキュリティ・ロック状態

### 7.1 初期状態

- 既定では、変更系操作はロック状態である。
- ただし、インセキュアビルドではこれを無効化してよい。

### 7.2 許可されるコマンド

- ロック中でも、以下のコマンドは受け付ける:
  - keyboard id query
  - definition size query
  - definition data query
  - unlock status query
  - unlock start
  - unlock poll
- ロック中に以下の書き込みを行ってはいけない:
  - keycode set
  - macro set
  - dynamic entry set
  - bootloader jump

### 7.3 解除手順

- unlock start で解除モードに入る。
- unlock poll で状態を確認し、必要なキーが押されている場合にカウントを進める。
- 最終的にカウントが 0 になると、unlocked = 1 とする。
- lock コマンドで unlocked = 0 に戻す。
- 追加の実装上の注意として、ホストは `QK_BOOT` / `RESET` 相当のキーコードを特別扱いする。キー・エンコーダ・動的エントリにこの値を割り当てた場合、ホストはアンロック/ブートローダ遷移を起動することがあるため、ファームウェア側でもこれを通常のキーコードではなく、ブート・リセット系の特殊値として扱うことが望ましい。

## 8. 推奨する実装動作

### 8.1 すべての応答で守るべきこと

- 受信パケットの長さが 32 バイトでない場合は何もしない
- 受け取ったコマンドが未定義であれば、0x00 または 0xFF で埋めた応答を返す
- 返却するバッファは、必要な箇所だけを書き、それ以外は 0x00 で埋める

### 8.2 使い方の典型フロー

1. ホストが `0xFE, 0x00` で keyboard ID を問い合わせる
2. ホストが `0xFE, 0x01` と `0xFE, 0x02` で keyboard definition を取得する
3. ホストが `0x04, 0x05, 0x06, 0x12` などの VIA コマンドでキーマップを読み書きする
4. 必要に応じて `0xFE, 0x0D` で動的エントリを取得・更新する
5. 変更後は `0xFE, 0x05` などで状態を確認し、必要なら `0xFE, 0x06` / `0xFE, 0x07` でアンロックする

## 10. 実装上の注意

- この文書は「内部の制御構造」ではなく「外部インターフェース」を規定している。
- 実装言語、ハードウェア、OS、通信ライブラリは問わない。
- 互換実装の主眼は、ホストから見た入力/出力の契約を一致させることである。
- 既存の Vial / VIA 互換クライアントが期待する値を返せるように、各コマンドのバイト位置・端数・状態遷移を厳守すること。

## 11. 追記したホスト視点の補足

- ホスト実装は、GET 系応答で「先頭にコマンド ID を返す」ことを前提にしており、バッファ取得系では `data[4:]` を実データと見なす。
- Dynamic Entry の個数取得では、複数のエントリ種別と機能フラグを 1 パケットで返す。これにより、ホスト側は事前にどの機能をサポートしているかを判断できる。
- QMK Settings は、`QUERY` → `GET` / `SET` / `RESET` の流れを前提にしており、`0xFFFF` 終端や `byte 0 = 0` 成功判定を仕様として明示すべきである。
- Lighting / VialRGB は、QMK / VialRGB の両方をサポートするホスト実装に合わせて、`value_id` と応答オフセットの解釈を明文化する価値がある。
